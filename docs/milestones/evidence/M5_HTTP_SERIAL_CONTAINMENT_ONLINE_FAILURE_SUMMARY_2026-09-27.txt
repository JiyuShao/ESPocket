Interpretation boundary
- The 1/1 setting prevented recurrence of the previously observed -0x008D TLS allocation failures in this run.
- It did not make the online Store path stable.
- The crashing task was actively inside Mbed TLS handshake through esp_http_client_open when it dereferenced an invalid/null-adjacent address.
- Locked-source timing matches the incident: Store starts a 31,000 ms watchdog for a 15,000 ms request with one immediate retry; the observed watchdog fired 31,017 ms after request id(3) submission while the sole HTTP worker was in the second TLS handshake.
- The watchdog runs App Store timeout handling in the SystemApp scheduler context. Its scheduler-free CancelRequest executes inline there, sets the cancel flag, copies the active transaction under a shared-pointer mutex, releases that mutex, and can call esp_http_client_close() without an operation mutex while the HTTP worker remains blocked in open().
- esp_http_client_close() destructively closes ESP-TLS and frees/zeros Mbed TLS state. ESP-IDF explicitly forbids simultaneous same-handle open/close operations. One worker/one active request does not serialize this SystemApp cancellation path against the worker.
- This makes close-versus-handshake invalidation the strongest and most likely cause, consistent with EXCVADDR 0x8. However, the trace does not contain the canceling worker's stack inside esp_http_client_close(), so the precise runtime overlap and exact invalid Mbed TLS member remain strongly supported rather than instruction-for-instruction proven.
- No further device reproduction is required: this run already rejects the containment as an M5 online-stability fix.
