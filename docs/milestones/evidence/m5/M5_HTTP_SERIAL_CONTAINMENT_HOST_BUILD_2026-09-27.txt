Confirmed root-cause boundary
- ESP-IDF 6.0.1 bundles Mbed TLS 4.0.0.
- `MBEDTLS_ERR_SSL_ALLOC_FAILED` maps to `PSA_ERROR_INSUFFICIENT_MEMORY`.
- `PSA_ERROR_INSUFFICIENT_MEMORY` is numeric -141, which is the logged -0x008D.
- The generated configuration selects `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC=y`, a 16,384-byte input content length, and a 4,096-byte output content length.
- ESP-IDF's Mbed TLS allocator therefore requests `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT`; PSRAM cannot satisfy these TLS allocations.
- Internal-RAM exhaustion during TLS setup is confirmed. It is not a certificate, DNS, or server-identity failure.

Cancellation concurrency boundary
- The failed image allowed two HTTP workers and two concurrent requests.
- App Store invokes `CancelRequest` asynchronously, but the HTTP service schema marks that function `require_scheduler=false`; Service Manager therefore executes it directly on the caller thread.
- HTTP cancellation sets the cancel flag, copies the transaction under its transaction mutex, releases the mutex, and calls `transaction->cancel()`.
- The ESP HAL transaction implements cancel with `esp_http_client_close(client_)`.
- Worker paths can concurrently execute transaction `open()`, `read()`, and `is_complete()` without the same mutex serializing those operations.
- ESP-IDF documents that the same HTTP client handle must never be operated simultaneously from two places and identifies open/read/close as phases of that one client operation. The Brookesia close-vs-active-operation path is therefore unsupported concurrent access to the same mutable handle, not merely a theoretical C++ lifetime concern.
- Shared ownership keeps the C++ wrapper alive but does not serialize the underlying ESP HTTP client state.
- Because no panic PC/EXCVADDR/backtrace was captured, this confirmed concurrency-contract violation is the strongest supported panic cause, but the exact faulting instruction remains unproven.
- The `Failed to stop App Store size metadata timer: 364` warning is not treated as UAF evidence: Core clears App timers before native `on_stop()`, after which Store attempts to stop its stale local timer ID.

Product containment
- No managed component was modified.
- Product defaults now set the official public Kconfig values:
  CONFIG_BROOKESIA_SERVICE_HTTP_WORKER_NUM=1
  CONFIG_BROOKESIA_SERVICE_HTTP_MAX_CONCURRENT_REQUESTS=1
- This limits active Store HTTP requests to one and prevents overlapping TLS setup peaks.
- It does not serialize scheduler-free `CancelRequest` with the sole worker's active transaction, so the upstream unsupported close-vs-use path remains. Device validation can show whether lower memory pressure avoids the observed failure, but cannot convert this containment into an upstream race fix.
- TLS verification, required time sync, and the full certificate bundle remain enabled. No insecure TLS option was enabled.
