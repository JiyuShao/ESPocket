# 06 — App 发现与 Launcher

## 目的

本契约定义固定产品入口和动态 App 何时能成为用户可见、可启动的 Launcher 条目，并保证安装、更新、卸载与失败状态的一致性。

## 用户结果

- Launcher 只显示可用且符合产品准入规则的 App。
- App 更新或卸载后，用户不会看到过期、重复或不可启动的条目。
- 动态 App 不可用时，固定系统入口仍然可用。
- 启动失败会留在可理解的位置并给出明确结果。

## 产品要求

| ID | Requirement |
|---|---|
| DSC-001 | Launcher 必须区分产品提供的固定入口与来自已安装状态的动态 App。Circular Shell 第一页显示四个固定入口，后续每页最多显示四个来自 Core 已提交投影的动态入口；分页不改变 App identity、安装状态或准入规则。安装集合变化后页码收敛到有效范围。 |
| DSC-002 | 动态 App 只有在可信、兼容、信息完整、已安装且未被产品策略隐藏时才可显示。 |
| DSC-003 | Catalog 条目、下载记录、缓存目录、未完成安装和孤立文件不得单独产生 Launcher 条目。 |
| DSC-004 | 每个 App 必须使用跨重启稳定的产品 identity；重复或冲突 identity 必须 fail closed。 |
| DSC-005 | Launcher 展示必须与完整、已确认的安装状态一致，不得根据单个事件猜测最终结果。 |
| DSC-006 | 安装、更新和卸载只有在相应状态完整提交后，才能改变用户看到的动态条目。 |
| DSC-007 | 选择条目时必须根据有效 App 状态解析启动目标，不得调用过期的运行期 identity。 |
| DSC-008 | 目标不存在、不可启动或 identity 冲突时，Launcher 必须保持可用 Surface 并提供可诊断结果。 |
| DSC-009 | 动态发现不可用或结果不完整时，固定产品入口必须继续保持可用。 |
| DSC-010 | 成功启动的 App 必须遵守统一的导航、Home、显示恢复与回收契约；开发者兼容旧包的导航例外按 [开发者安装例外](05-runtime-package-trust.md#开发者安装例外) 执行，仍须有真实启动与 Home 退出。 |

## AI Native

| ID | Requirement |
|---|---|
| DSC-011 | AI 能力的可发现性必须跟随对应 App 的可信、已安装、兼容和可用状态。 |
| DSC-012 | AI 能力可被发现不得被解释为用户已经授权执行；具体 Action 必须单独授权。 |
| DSC-013 | App 更新或卸载后，Assistant 不得继续展示或调用旧版本能力。 |
| DSC-014 | 固定 UI 入口、Launcher 条目和 AI 能力可以有不同展示方式，但必须共享同一 App identity 与可用性事实。 |

## 非目标

- 规定刷新周期、事件总线、快照算法、排序容器或 UI 子树更新方式。
- 让 Launcher 负责包验证、文件清理或安装修复。
- 在信任和可用性未知时猜测动态 App 状态。
