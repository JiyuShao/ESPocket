# 02 — AI Native 产品要求

## 目的

AI Native 让 Assistant 成为 ESPocket 的一等访问方式。它通过稳定产品语义理解状态、请求动作和观察结果，同时维持用户控制、安全规则与 UI 可用性。

## 用户结果

- 用户可以表达目标，不必描述页面、坐标和手势步骤。
- 用户知道 Assistant 将做什么、需要什么授权，以及动作最终是否完成。
- 用户可以取消尚未越过不可逆边界的操作，并在结果不确定时获得明确提示。
- 用户关闭、卸载或停止某项能力后，旧的 AI 访问不再生效。

## 产品要求

| ID | Requirement |
|---|---|
| AIN-001 | Assistant 必须通过面向用户结果的稳定语义访问能力，不能把界面坐标、手势序列或内部对象当作产品能力。 |
| AIN-002 | Context、Action 与 Event 必须使用用户能够理解的名称、状态和结果。 |
| AIN-003 | 每次 Action 必须保留实际调用者身份，并在 User Intent 与 Scoped Grant 范围内执行。 |
| AIN-004 | 会造成显著费用、数据损失、隐私暴露、外部通信或设备状态重大变化的 Action，必须在执行前获得明确确认。 |
| AIN-005 | Context 读取必须遵循数据最小化；未授权的敏感信息不得因 Assistant 可访问而扩大暴露范围。 |
| AIN-006 | Action 结果必须区分成功、未执行、失败、已取消和结果不确定，不能把请求已接收当作动作已完成。 |
| AIN-007 | 可取消 Action 必须说明取消边界；越过不可逆边界后不得报告为已取消。 |
| AIN-008 | 能力停止、实例回收、权限撤销、更新或卸载后，Assistant 必须立即失去相应的调用与观察能力。 |
| AIN-009 | AI 能力可被发现不得自动产生执行权限；授权必须在具体 Action 上单独判断。 |
| AIN-010 | 用户必须能够识别 Assistant 正在处理、等待确认、完成、失败或结果不确定的状态。 |
| AIN-011 | AI 路径必须与 UI 路径共享同一产品约束、风险等级和最终状态，不得形成隐藏的特权路径。 |
| AIN-012 | AI 服务不可用时，产品必须保持基础 UI、系统导航和关键恢复能力可用。 |
| AIN-013 | 新增或修改产品能力时，必须同时定义 AI 语义、授权、风险、生命周期、取消和结果表达。 |
| AIN-014 | 明确不开放或延期开放的能力也必须保留可追踪的 Exposure Decision，不能因遗漏而默认暴露。 |

## 非目标

- 指定大模型、语音服务、传输协议或工具调用框架。
- 让 Assistant 直接操作未注册的内部 Interface。
- 以 AI 能力替代用户可见的基础交互和恢复路径。
- 保证任何 App 或 Brookesia Service 永久驻留。
