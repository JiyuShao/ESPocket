# 01 — ESPocket 产品总览

## 目的

ESPocket 是面向 ESP 系列轻量智能设备的应用平台。它提供一致的系统体验、App 模型和 AI Native 访问方式，使有限资源设备仍能可靠承载本地交互、Native App、Runtime App 与系统能力。

## 用户结果

- 用户始终能够识别系统所处位置，并返回稳定的 Home 与恢复路径。
- 用户面对的是一致的 App 体验，不需要理解不同执行模型。
- 用户可以通过界面或 Assistant 使用获准的产品能力。
- 可选能力不可用时，设备仍能提供可理解的基础体验。

## 产品要求

| ID | Requirement |
|---|---|
| OVR-001 | ESPocket 必须提供统一的系统体验、App 运行环境和设备能力入口，而不是若干互不相干的示例集合。 |
| OVR-002 | 网络、时间或其他可选能力不可用时，产品必须保留可识别的 Home、基础导航和恢复路径。 |
| OVR-003 | Native App 与 Runtime App 的执行差异不得改变用户看到的导航、生命周期和失败语义。 |
| OVR-004 | 本地 UI 与已注册的 AI 能力必须使用同一产品语义，任一路径不可成为另一条路径的运行前提。 |
| OVR-005 | 外部内容、第三方 App 与网络输入不得削弱设备的可信基线和固定系统入口。 |
| OVR-006 | 产品应该针对 466×466 圆形触摸屏优化，同时保持核心产品语义不依赖特定屏幕形状。 |

## AI Native

| ID | Requirement |
|---|---|
| OVR-007 | AI Native 必须作为所有产品能力的基础设计维度，与 UI、安全、生命周期和恢复语义同时定义。 |
| OVR-008 | 每项产品能力必须明确 Exposure Decision：开放稳定语义、明确不开放，或延期处理。 |
| OVR-009 | UI 与 Assistant 使用同一能力时必须得到一致的产品结果，并按实际调用者分别授权。 |
| OVR-010 | Assistant 不可用或执行失败时，用户仍必须能够使用基础 UI 和关键恢复路径。 |

## 非目标

- 规定底层框架、硬件抽象或内部 Manager 的实现方式。
- 把某一种 Shell、屏幕形状或 AI 供应商定义成 ESPocket 本身。
- 因底层 Interface 存在就自动承诺 Pet、XiaoZhi、MCP 或其他独立产品体验。
